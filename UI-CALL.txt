3. REMAINING IMPLEMENTATION ITEMS
------------------------------------------------------------------------------

	mm runs APP_PROCESSES app processes from the $DEPLOY@.service template,
	each on its own unix socket. nginx sends other routes round robin and
	each /call_signal/<call_id> to the process given by a hash of the call
	id, with no retry on another process. Each process records its
	APP_INSTANCE in the sessions whose open call it holds, and
	webb_call_repair() clears only those. Known issue:
	push_rowset_changed_events() wakes only the /rowset.events listeners of
	its own process. Untested on a real deploy.

	Manual acceptance. Cosmin verifies visual and interaction behavior
	interactively. No screenshots for canvas-ui verification. Any requested
	browser automation reads state and media statistics instead.

	Case                    | Acceptance to check
	------------------------|-------------------------------------------------
	 Two-person call        | Both participants hear and see each other.
	 Audio-only entry       | Audio works with camera absent, denied or off.
	 Group call             | Join/leave and media work through the SFU.
	 P2P/SFU threshold      | Switch at six -> seven -> six peers.
	 Mute/camera controls   | Correct transmission and actual state indication.
	 Device replacement     | Selected device works; loss/failure is visible.
	 TURN-only connection   | Audio/video work with relay candidates forced.
	 Blocked audio playback | User can enable sound explicitly, without echo.
	 Resize/hidden tiles    | Correct layout/audio per chosen policy.
	 Socket interruption    | Bounded recovery; preserve still-working media.
	 Reload/duplicate tab   | Follow the selected identity/replacement policy.
	 Leave during capture   | Stop late capture results; no camera/mic leak.
	 Expiry/access denial   | Refuse entry/resume; terminate local resources.
	 Server restart         | Check the recovery contract selected for D11.


4. TEST PLAN
------------------------------------------------------------------------------

Test the browser/provider integration first. Then put most coverage into
controlled transitions. Use real Web Crypto for cryptographic checks.
Cosmin verifies canvas-ui appearance and interaction; browser automation
reads state, decoded video counters and received audio samples.

Order | Coverage                     | Method
------|------------------------------|----------------------------------------
 1    | Actual media paths           | Two real browsers and real Cloudflare.
 2    | Pending operations           | Control time and network completion.
 3    | Encryption and key lifetime  | Known vectors and invalid-frame cases.
 4    | Repeated transitions         | Seeded sequences and real media soak.

Real browser/provider checks

	- Use Chrome and Firefox. Start with two peers; Force SFU avoids the
	  need to run seven browsers for every media integration check.
	- Verify P2P, forced TURN, SFU, and SFU through forced TURN.
	- Verify bidirectional media, audio only, video only, receive only,
	  and both peers idle before either enables capture.
	- Switch P2P -> SFU -> P2P while transmitting and while receiving.
	- Disable capture for more than 30 seconds, then enable it again.
	- Verify received decoded video frames and received audio samples.
	  Check connection state and measured bitrate as additional evidence.
	- In Chrome, read received audio samples through
	  createMediaStreamSource() on the received track while an audio
	  element plays that track. Chrome decodes remote audio only while an
	  element plays it. The node created by createMediaElementSource() for
	  an element playing a MediaStream outputs only zeros.
	- Check permission denial, device removal, device replacement, camera
	  blur and blocked audio playback interactively.

Controlled transition checks

	Control the clock, signaling delivery and Cloudflare response delivery.
	Exercise the actual call code at those boundaries. Keep the real browser
	checks above to verify WebRTC behavior and the provider API contract.

	Operation pending       | Events before completion
	------------------------|-------------------------------------------------
	 Capture or blur setup  | Disable, change device, change blur, leave.
	 SFU session creation  | Leave, change mode, lose signaling, reconnect.
	 Publish or subscribe  | Source leaves, source restarts, change mode.
	 Offer/answer exchange | Lose signaling, peer replacement, ICE failure.
	 Track closure         | Source replacement, partial error, leave.
	 Media key delivery    | Join, leave, reconnect, delayed/duplicate reply.

	For each operation, complete it successfully, fail it, and complete it
	after its owner has left or has been replaced. Include partial track
	allocation and partial closure. Advance time across heartbeat, repair
	and reconnect deadlines without fixed sleeps.

	Check these invariants:
	- Old operations never modify the current connection or peer.
	- The server selects P2P through six peers and SFU above six peers,
	  unless the call-wide Force SFU override is enabled.
	- Changing that override above six updates everyone without rebuilding
	  an unchanged media connection.
	- Every allocated track remains owned until closure is confirmed.
	- Leave releases captures, workers, connections and pending requests.
	- An idle SFU peer owns no Cloudflare session until media is needed.
	- Reconnect preserves identity within the reconnect window.
	- Encryption never falls back to plaintext when keys are unavailable.

Cryptographic checks

	- Check round trips for Opus frames and for VP8 keyframes and delta
	  frames, including frames shorter than the VP8 header.
	- Reject truncated frames, a wrong key, modified ciphertext, modified
	  unencrypted header bytes, a modified nonce and invalid tags.
	- Install transforms before the first frame on every sender/receiver,
	  including those created during mode changes and capture replacement.

Repeated transitions

	Run reproducible sequences of joins, departures, capture toggles,
	signaling loss and mode changes. Record the seed and operation order.
	Also run a longer real-browser call and check that resources are
	released after each departure and after the final leave.


5. ENCRYPTION IMPLEMENTATION PLAN
------------------------------------------------------------------------------

Goal: Cloudflare cannot decrypt audio/video. The Lua server creates and
distributes the media keys. Cloudflare can still observe routing
metadata. The Lua server continues to exchange signaling and Cloudflare
control requests, with no media-frame forwarding.
Browsers must load trusted application code.

Stage | Work                                             | Status
------|--------------------------------------------------|--------------------
 1    | AES-GCM frames with unencrypted VP8 header       | Done
 2    | Chrome/Firefox/Cloudflare packetization check     | Done
 3    | Server-created meeting key                       | Done
 4    | Encoded-transform worker and call integration    | Done
 5    | Readiness display and transition coverage        | Planned

Stage 1: frame format and cryptographic operations

	Frame on the wire: [unencrypted VP8 header][AES-GCM ciphertext and
	16-byte tag][12-byte random nonce]. The VP8 header is 3 bytes, or 10
	bytes on a keyframe, and the code authenticates it as additional data.
	Opus frames have no unencrypted bytes. Every frame uses the meeting's
	media key and a fresh random nonce. With random 96-bit nonces, one key
	is safe for about 2^32 frames.

	Implementation: www/ui_call_e2ee.js, tested by
	tests/ui_call_e2ee_test.mjs. This module does not change live calls.
	The call module must not advertise E2EE before integration.

Stage 2: packetization and browser compatibility

	Encrypted calls use only Opus and VP8. The H.264 and AV1 packetizers
	split frames at markers inside the frame bytes, and encrypted frames
	contain no such markers. H.264 for phones needs encryption that keeps
	the H.264 headers in the frame unencrypted; that depends on the
	browser-targets decision.

	Chrome's receiver takes the VP8 keyframe flag from the dependency
	descriptor RTP header extension when that extension is negotiated, and
	otherwise from the first frame byte. Keep the VP8 header unencrypted
	so that Chrome reads the real flag on every path.

	Full-frame SFrame result in Chrome 148 P2P: neither connection
	negotiated the dependency descriptor. Chrome decoded 252 of the first
	299 frames as keyframes. After 5 dropped frames, Chrome sent 3 PLIs
	and decoded no frame in 10 seconds. The plaintext control recovered
	after 1 PLI.

	Result with the unencrypted VP8 header: Chrome 148 and Firefox 140
	recovered after 5 dropped frames in every completed scenario, P2P and
	through Cloudflare, plaintext and encrypted. No connection negotiated
	the dependency descriptor.

	Firefox 140: in 2 of 4 runs the page never reported, and the runner
	stopped Firefox after 240 seconds. A standalone probe showed the
	cause: when the page creates an RTCRtpScriptTransform before its
	worker script has run, Firefox often never starts the transform. No
	frame then passes through any transform, the video element paints
	nothing, and getStats() on both connections never resolves. This
	happened in 15 of 19 runs. In 6 of 6 runs where the page waited for a
	message posted by the worker script before creating the transforms,
	media flowed. The test page now starts one worker per scenario and
	waits for its ready message; Firefox then did not stall in 7 runs. The
	production worker needs the same wait.

	One of 3 Cloudflare runs failed in both browsers with "SFU publisher
	connection timed out", with no ICE candidate errors. Cause unknown.

Stage 3: key distribution

	Only Cloudflare is excluded from the media. The site is not served
	through Cloudflare's proxy, so Cloudflare cannot read signaling.

	The Lua server creates a random 16-byte media key when a meeting
	starts and keeps it in memory with the room. The server sends the key
	over signaling to each admitted member. Never reuse the invite_token
	query parameter as the media key. Never send the key to Cloudflare.
	Browsers keep the key in memory, never in browser storage.

	Every sender encrypts with the media key and a random nonce per frame,
	so senders need no key ids or counters.

	The server controls admission and Cloudflare track subscriptions, so
	the media key stays the same when members join or leave.

	Implementation: lua/webb_call.lua creates the key with the in-memory
	call and sends it in every 'joined' message, including after a
	reconnect. When the last peer leaves, the server removes the call and
	its key; the next join creates a new key. www/ui_call.js stores the key
	from 'joined' in memory. Nothing reads it until stage 4.

Stage 4: worker and media integration

	Encrypt only SFU media. WebRTC encrypts P2P media between the two
	browsers with DTLS-SRTP, and Cloudflare TURN relays only forward those
	encrypted packets.

	Use RTCRtpScriptTransform and Web Crypto in a dedicated worker. Attach
	encryption immediately when creating a sender, and attach decryption
	before processing the receiver's first frame. Cover SFU publishers and
	SFU subscribers. replaceTrack() keeps a sender's transform.

	Drop unauthenticated frames.
	Unsupported browsers cannot enter an encrypted call. Close the worker
	and discard keys on leave. Check asynchronous completions against the
	current call before accepting them.

	Implementation in www/ui_call.js: start_sfu() creates one
	www/ui_call_e2ee_worker.js per SFU connection and waits for its ready
	message before publishing or subscribing. sync_sfu_publications()
	limits each sender to Opus, or to VP8 with RTX, and attaches the
	encrypting transform. The SFU connection's ontrack attaches the
	decrypting transform. stop_sfu() terminates the worker. The worker
	drops frames that fail authentication. 'joined' delivers the media
	key before any SFU connection starts, so no sender waits for a key.
	A browser without RTCRtpScriptTransform fails the call when the call
	switches to SFU. Cosmin verified SFU audio/video in a real call.

	Chrome passes padding-only audio RTP packets to the receive transform
	as empty frames. The receive worker passes an empty frame through
	unchanged, and Chrome then discards it as it does without a transform.

	Account for encryption/decryption work per encoded frame and for the
	12-byte nonce plus the 16-byte authentication tag. Keep encryption in
	the worker; do not add per-frame work to the canvas-ui build pass.

Stage 5: verification and acceptance

	Show encryption readiness.
	Apply the cryptographic and transition checks in section 4, then verify
	actual decoded audio/video through Cloudflare in Chrome and Firefox.
	Do not equate successful connection setup with successful decryption.
