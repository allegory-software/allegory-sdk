NAV INSERT/MOVE ROW OPS
==============================================================================

Review of www/ui_nav.js and www/ui_grid.js, 2026-10-03.
Source inspection only. Cosmin tests the grid interactively.

Gestures in scope:

- Insert: insert before the focused record, under the same parent.
- Down at the bottom: append a record. For a filtered flat nav, append to
	the complete list. Continuing the last tree parent's children is N1.
- Drop between rows: move between siblings at the indicated tree depth.
- Drop on a record: move as a child of that record.

The grid has not connected row dragging yet. Move findings below describe
the existing nav code used to implement these gestures, not working mouse
interactions today.

Directions from this discussion:

- Keep temporary insertion placement until the next visible-row rebuild.
- Prefer keeping unsaved new rows visible through ordinary column filters.
- Consider displaying new rows with missing keys or positions first within
	their parent after a rebuild; see N7.

In the current invariants, insertion placement lasts until the next sort
and custom movement is prohibited while filtered. Update those rules after
deciding the new behavior and before implementing it.


OBVIOUS BUGS / GAPS
------------------------------------------------------------------------------

A4. Connect row dragging and preserve tree sibling order after a drop.
	Status: PARTIAL. Sibling ordering is implemented for same-parent moves
	and for parent changes.
	Done: in unsorted trees with pos_col or client-side array order, place
	moved siblings at the drop position in the complete child array before
	copying stored order and numbering positions. Retain their complete
	subtrees, including collapsed children. Root moves use the root array.
	Cost: same-parent moves use O(s) sibling searches and array shifts, plus
	a scan of the moved visible rows to count siblings. array_move creates
	a temporary array containing the moved siblings. When changing parent,
	the nav removes the k siblings from the old child array with one shift
	and inserts them into the new one with one shift. No added
	allocations. Existing visible-index updates and the client-tree
	stored-order rebuild cost O(n).
	Remaining: connect drag start, destination preview, drop and
	cancellation. Use state.can_drop(insert_ri, parent_row) when choosing
	drop targets, and state.cancel() to cancel. Between start and finish,
	row_index() returns null for the cut rows and the rows after them:
	start_move_selected_rows() cuts e.rows without updating indices.
	User: drag a row between siblings or onto another row, then trigger a
	visible-row rebuild.
	Current: the grid never starts a row drag or completes a drop. Server
	tree navs keep all_rows unchanged; client tree navs rebuild it from
	child_rows. On flat moves in custom order, finish() commits display
	order to all_rows.
	Source: www/ui_nav.js:2176,3720,3738,3739.

B1. Hidden records after filtered insertion or without a detail master.
	User: press Insert or Down while a column filter excludes a blank row,
	or press Insert in a detail grid with no selected master.
	Current: the nav adds the record to all_rows but omits it from visible
	rows. It can focus the old record again, allowing repeated Down to add
	hidden records, which a server grid saves. With param_vals false, the
	nav hides every insert and cannot fill the missing master values.
	Required: apply the preferred unsaved-row visibility rule to ordinary
	column filters, immediately and during later rebuilds. Refuse UI
	insertion without a detail master.
	DECIDE: confirm keeping unsaved new rows visible through column filters.
	Source: www/ui_nav.js:1273,2525,2549,3247,3319,3340.

A13. Temporary insertion placement after a visibility-only rebuild.
	Requested behavior change; A2 remains fixed under the current rule.
	User: insert while sorted, then change a filter or collapse another row.
	Current: the nav also inserts at that position in child_rows. Rebuilding
	visible rows from child_rows, the nav retains that position without
	sorting.
	Required for the requested lifetime: rebuild from ordinary display
	ordering; retain no insertion-position history beyond the rebuild.
	Source: www/ui_nav.js:3305,3314,949.

A12. Server sibling reordering without pos_col is not persistent.
	Status: PARTIAL.
	Done: can_actually_move_rows() disables movement in flat server navs
	without pos_col and reports that saving row order requires a position
	column. Client navs can still move rows using array order.
	state.can_drop(insert_ri, parent_row) checks the allowed range, parent
	permission and parent eligibility. Without client array order or
	pos_col, the helper permits only a parent change. The grid supplies
	the destination parent; the visible index alone is ambiguous in trees.
	Cost: O(1) per target with no allocations. One function per drag.
	Remaining: query the helper when connecting grid drop targets in A4.
	User: reorder server rows between siblings, save, then reload.
	Current: the grid has not connected row dragging. finish() assumes
	an allowed destination and does not repeat the target checks.
	Source: www/ui_nav.js:1351,1367,3708.


NICE-TO-HAVE
------------------------------------------------------------------------------

N1. Continue the last sibling list with Down at the bottom of a tree.
	User: focus the last visible child and press Down to add another child
	under the same parent.
	Current: the grid passes no anchor, so the nav appends a root record.
	Needed: derive the parent from the focused row and append to its complete
	sibling list. This is a chosen behavior change, not a current invariant.
	Source: www/ui_grid.js:1421; www/ui_nav.js:3213,3235.

N2. Reorder while filtered, including client detail navs.
	User: filter the grid and drag a visible record between visible siblings.
	Current: the nav prohibits every filtered move.
	Needed: resolve the visible destination to complete sibling order and
	move only the selected records, keeping unselected hidden records in
	relative order. After removing the filter, the nav must display that
	complete order.
	Source: www/ui_nav.js:1315,3731.

N3. Insert or reorder within one leaf group.
	User: focus a row in a leaf group and press Insert, or drag a row
	between other rows in that group.
	Current: the nav prohibits grouped insertion and movement (A6).
	Needed: for insertion, fill grouped values from the focused row and
	attach through the grouping code. For movement, update row order within
	the same group and under the same real tree parent, with editable order
	displayed.
	Source: www/ui_nav.js:1273,3232,1995,1341.

N4. Drop onto an exact-value group header to change grouped values.
	User: drag a row onto another group's header.
	Current: the nav has no group-aware completion for this gesture.
	Needed: update the actual grouped fields and row order, and refresh
	group membership, while preserving real tree parentage. Require
	writable grouped fields. For a range group, decide which actual field
	value to assign before enabling that destination.
	Source: www/ui_nav.js:1964,1995,3688.

N5. Change parent while explicitly sorted.
	User: sort a tree, then drop a record onto another parent.
	Current: the nav prohibits every sorted move.
	Needed: allow the parent change and place the subtree using the current
	sort under the destination. Keep sibling reordering by drops between
	rows unavailable while sorted.
	Source: www/ui_nav.js:1315,2137,2249.

N6. Drag a noncontiguous selection.
	User: Ctrl-select separated siblings and drag them together.
	Current: the move code represents one contiguous visible range.
	Needed: operate on selected records, preserve their relative editable
	order, include complete subtrees, and exclude selected descendants whose
	ancestors are already moving. B11 currently refuses these selections.
	Source: www/ui_nav.js:1538,3627,3761.

N7. Keep incomplete new rows easy to find after rebuilding.
	User: insert a record with missing key or position values, then change
	the sort or trigger another visible-row rebuild before completing it.
	Current: the nav has no common rule for putting such records first.
	Needed: display those unsaved new records first within their parent.
	Use current row state; retain no previous insertion-position history.
	Source: www/ui_nav.js:3297,939,952.

N8. Avoid work on every row for a small insertion or drop.
	User: insert one record or drag it one sibling away in a million-row nav.
	Current: the nav rewrites all visible indices; movement can also copy
	all_rows or rebuild it from the tree, and renumber positions.
	Needed: choose order storage and visible indexing together.
	With an internal position slot alone, the nav still shifts arrays and
	updates indices. With dense positions, it can need many field updates.
	Current work is O(n), with n the number of records, in these paths.
	Source: www/ui_nav.js:1257,3707,3732,3741,3613.

S. SAVING (open, later)
------------------------------------------------------------------------------
S1. pack_changes skips a row whose save request is in flight. Nothing
	retries a failed save.
S2. An edit made while the row's save is in flight is lost: apply_result
	clears modified, takes the row out of changed_rows, and overwrites the
	input value if the server returns values.
S3. With two save requests in flight, the server may process the later one
	first, e.g. a parent's delete before its child's. The server keeps the
	tree consistent, so the result is a spurious error, not a broken tree.
S7. validate_row() reuses stored client results, so a lookup value that
	was valid when set is not re-checked at save. Nothing revalidates a
	column when its lookup nav's rows change (TODO at
	www/ui_nav.js:3085).


P. PERFORMANCE AT 1M ROWS (open)
------------------------------------------------------------------------------
P4. update_row_index() writes into every visible row on every insert and
	move: 18 ms at 1M rows in memory order, 83 ms after a sort (measured).
	On removal, collapse and filtering, update_parts() also rebuilds e.rows
	from the whole tree. Proposal: a block index next to e.rows, blocks of
	~1000 rows, each row storing its block and its offset in the block; on
	insert or removal the code rewrites one block and the block starts.
	See N8.
	Source: www/ui_nav.js:1278,939.
P6. update_all_pos_fields() calls set_cell_val() on every row on every UI
	insert and UI removal with pos_col. With dense positions, after an
	insert near the top the nav changes and saves n positions.
	DECIDE: dense or sparse positions. See N8, A3.
	Source: www/ui_nav.js:3612.
P8. A static rowset's save() serializes every row, and the nav saves on
	every row exit by default.
	Source: www/ui_nav.js:4410.
P9. Rows become holey arrays: the code writes the row index slot and the
	cell-state slots past the end of the row, leaving gaps. In a
	measurement, packed rows were no faster (first index write 129 ms vs

	DECIDE: keep rows packed anyway?

NAV2 SLOT RETIREMENT
==============================================================================

NAV2-D1. Removing a parent and a selected new descendant queued that
	descendant twice. drop_rows() freed its slot twice and decremented its
	modified count twice. A later insertion could assign one slot to two
	rows and loop forever during tree traversal.
	Status: FIXED.
	The nav compacts row lists and indexes before freeing data row slots.
	It clears each row's removal mask entry when freeing the slot, so
	each data row is freed once. free_slot() clears edits, errors and
	modified bits and updates modified_n. All group removals use the same
	operation.
	Cost: existing compaction scans, plus one pass over requested rows
	and O(k * f) cleanup for dropping k rows with f fields; no new arrays.
	The nav clears sparse state on removal instead of on slot reuse.
	Source: www/ui_nav2.js:930,1158.

NAV2-F1. Regrouping and grouped merges could reuse a focused or selected
	group slot before clearing references to the removed group.
	Status: FIXED.
	The nav commits the selection rectangle before freeing slots and
	clears their visible indices. focus_cell() with 'deselect_hidden'
	clears hidden focus and selection before slot reuse. The nav keeps
	the old visible list until cleanup finishes.
	Cost: one extra old-visible-row scan when regrouping with selection
	bits. Ordinary visibility updates use their existing scan. No new
	state or arrays.
	When ungrouping, the nav cleans selection only after rebuilding
	visible rows; no group slots are reused during that operation.
	During merges, the nav removes old groups and deleted data rows,
	clears hidden focus and selection, then allocates new rows and groups.
	The nav rebuilds the tree and visible rows once at the end. Standalone
	removals rebuild immediately after drop_rows().
	Cost for grouped merges without deletions: one extra old-visible-row
	scan when selection bits are present. Merges with deletions use their
	existing two selection scans and one tree and visible-row rebuild.
	Source: www/ui_nav2.js:1356,1832,1985.

The nav2 benchmark includes edited and selected row drops, insertion into
freed slots, ungrouping with selection, and subtree drops with new rows.
